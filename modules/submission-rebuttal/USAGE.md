# 投稿与审稿回复 · 使用说明

[模块首页](README.md) · [技能中文索引](SKILL_INDEX.md) · [教学示例](examples/README.md)

先确定当前是投稿前自查、首次回复、后续轮次还是重投准备。只加载适合当前阶段的入口，保留原始意见、证据版本和实际修改记录。

## 1. 准备输入

| 输入 | 应写清什么 |
|---|---|
| 稿件与版本 | 主文件、补充材料、图表、引用、版本或摘要；审稿人看到的是哪版。 |
| 证据材料 | 结果与分析位置、指标和范围、原始产物、限制；哪些材料尚未完成。 |
| 原始意见 | 审稿人标识、轮次和原文；编辑/领域主席意见与普通审稿意见分别记录。 |
| 投稿条件 | 目标场所与届次、官方链接、核对日期、截止时区、字数/字符规则、附件与匿名要求。 |
| 修改范围 | 已完成、拟进行、仅作未来工作的事项；作者已确认哪些承诺。 |
| 输出位置 | 自己研究项目的工作目录；不要将私人稿件和真实意见写回公开示例。 |

未指定目标场所时可做内部问题分析和通用回复练习，但不能生成“已符合某会议限制”的最终声明。真正投稿时从官方页面与平台字段核对规则；旧快照中的默认会议、限字数和回复布局不能直接沿用。

## 2. 投稿前先自查

使用 `paper-self-review` 与 [投稿前自查表](templates/pre-submission-check.md) 检查结构、证据、引用、图表和文字。每个问题记录位置、影响、处理和状态；对主张分别给出保留、削弱、修改或删除建议。

统计问题回到 [数据分析模块](../data-analysis/README.md)，缺实验回到 [实验模块](../experiment-design/README.md)，叙述重构回到 [写作模块](../paper-writing/README.md)。不能为了让清单全绿添加不适用的检验、编造引文或抹去负结果。

## 3. 拆分意见并建立证据矩阵

用 [意见与证据矩阵](templates/reviewer-evidence.csv) 为每个原子问题分配稳定 ID，例如 `R1-C2`。保留原文位置，记录类型、优先级、策略、证据和未决事项。一段意见有多个问题时拆成关联行；不同审稿人提出相同问题时可共享证据，但各自回复仍须可独立理解。

证据分为已有稿件、已完成实验/分析、已核对文献、带状态的计划和 unresolved。文件存在只说明有材料，不能自动推出统计有效或主张成立。只有摘要级文献时，不把它写成已经全文验证的结论。

## 4. 先定策略，再写逐条回复

用 `review-response` 完成分类和表述，或按 ARIS `rebuttal` 轻量模式先整理问题板与策略。回复按 **直接回答 → 证据与定位 → 对稿件的影响 → 仍未完成的事项** 写入 [逐条回复模板](templates/response-template.md)。

认可正确批评时直接说明已纠正的内容。存在合理分歧时解释定义、设计和证据范围，不以“模型认为没问题”代替论证。证据不足时收窄主张、承认局限或保留未决项。

`already_done` 应有可核验产物；`approved_for_rebuttal` 是已确认但尚未完成的承诺，不能写成过去时；`future_work_only` 不算本轮已经解决；`unconfirmed` 不进入确定承诺。模板状态用于记录，不能代替真实授权或执行。

## 5. 修订与回复保持一致

在 [修改记录](templates/revision-log.csv) 为每项实际修改关联意见 ID、旧位置、新位置和证据。未修改但作出解释的意见也要有去向，例如 `clarified_without_edit`；计划做而未做的修改维持 `planned` 或 `blocked`。

双向核对：每条“已修改”都能找到新稿位置，每个新增结果都能回到产物，每个承诺都出现在记录中，每个意见都有回答、明确延后或待补材料状态。不要把“已回复”与“审稿问题已被证据解决”混为一谈。

## 6. 核对投稿条件与审阅范围

填写 [投稿条件核对表](templates/submission-conditions.md)。明确字数还是字符数、是否计算空格/格式、每个审稿人单独限额还是共用限额、允许哪些链接或附件。按实际平台方式计数并保留检查记录，不从示例推定当前规则。

采用上游完整工作流时，记录实际审阅后端、输入版本、执行范围和结果。审阅未做或后端不可用时如实标记，不能伪造 PASS。渲染或编译成功仅说明相应产物在该环境可生成；不代表内容正确、匿名检查完成或已经提交。

准备好稿件和回复后仍按真实操作区分“草稿完成 / 条件待核对 / 可供人工检查 / 已实际提交”。本轮整理不涉及平台登录、发送审稿回复或远程投稿。

## 7. 可复制的自然语言指令

### A. 投稿前只读自查

```text
请先阅读本仓库 modules/submission-rebuttal/SKILL_INDEX.md，按 paper-self-review
检查稿件：[位置及版本]。分析证据：[位置]；图表和引用：[位置]。
按结构、主张、数字、引用、图表和表述给出问题、证据位置及建议。
区分需要统计重算、补实验和仅改表述的事项；不编造数据或引用，不替我声称已投稿。
本轮只交付自查清单和建议，不自动改写或发送文件。
```

### B. 从审稿意见到可核验回复

```text
请读取 submission-rebuttal 索引，用已有技能整理以下审稿意见：[位置]。
稿件版本：[填写]；结果和分析产物：[填写]；当前轮次：[填写]。
目标规则的官方来源与核对日期：[填写；未知则保留待核对]。
先拆解带 ID 的问题，建立证据矩阵，再写逐条回复和修改记录。
已完成的修改：[填写]；已确认但未完成的承诺：[填写]。
缺乏证据的事项标为 unresolved；未做实验不能写“我们已补充”。
规则不完整时只形成内部草稿，不声称满足最终限字或投稿条件。
输出到：[项目目录]；不要发送回复或进行投稿操作。
```

### C. 修订后交叉检查

```text
请核对原始意见、回复草稿、修订稿和修改记录：[各文件位置]。
检查每项意见的去向、每个事实的证据、每个“已完成”的新稿位置、每个承诺的实际状态。
列出遗漏、矛盾、过度主张和仍未执行的事项；区分回复覆盖与证据解决。
若审阅未执行，明确记录未执行，不用自查意见替代外部审阅结果。
```

这些是自然语言任务模板，不要求斜杠命令已安装。可先阅读 [三条模拟意见示例](examples/mock-review-walkthrough.md)，再将结构用于自己的真实材料。
